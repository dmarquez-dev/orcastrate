### Findings

Advisory:
- A1. StrictMode double-start: `main.tsx:23` mounts StrictMode and `workspace-provider.tsx:110-113`
  calls start then stop. That sends `pods.list` and the pulls twice in dev. `podCommandsPushes` is
  per store instance and never reset by `stop()`, so the comparison at send and at answer stays
  correct. The startup `pods.list` was already doubled before this change. Judged harmless.
- A2. A non-empty pull answer for a Pod deleted between `pods.list` and the reply re-creates its
  runtime record, because `patchRuntime` creates missing records (store.ts:385). This mirrors a
  push. The implementer disclosed it as an assumption, and no criterion covers it.

  synchronously in `start()` before any read is sent (store.ts:334-344). The counter is keyed per
  Pod (store.ts:242, :577). Both hold.
- A4. Disclosed coverage gap: nothing tests that a Pod created after start issues no pull. No T2
  criterion asks for it.
