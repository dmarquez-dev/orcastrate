### Blocking findings

**B1 — A test name claims every border width in the file goes through a token, while its own
assertion lists `border: 0`, a literal.** `Composer.styles.test.ts:84-92`. The file's own code
classifies that declaration as a border width: the extractor is `BORDER_WIDTH_DECL` and its
docstring at `:20-25` reads "Every border-width-bearing declaration in this file". This is the
universal-in-a-name overclaim criterion 7 exists to stop, and it is in the test this task
**wrote**, not the one it renamed. Not `amendment-caused`. Orchestrator independently verified the
name and the array before opening the round.

Remediation options, as the reviewer worded and ranked them:

1. *(best, per reviewer)* **Rename to what the assertion checks**, e.g.
   `declares exactly these four border-width values, every keyword site among them a token`.
   Keeps the equality assertion's extra strength while the name no longer asserts a universal the
   list refutes. Evidence `repo`: `beachcomber/Beachcomber.styles.test.ts:38` and `:46` both name
   their tests for the literal forms they match rather than for a property of the whole file.
2. **Keep the universal but make it true by excluding the zero case**, e.g.
   `states every non-zero border width in this file through a token`. One word, no assertion
   change; slightly weaker as documentation because the reader must go to the array to see which
   declaration the exception is. Evidence `repo`: the file's own `BORDER_WIDTH_DECL` docstring
   already distinguishes width-bearing declarations from the rest.
3. **Drop the name's claim entirely**, e.g. `pins the file's border-width declarations`. Safest
   against future drift, but loses the token invariant from the name, which is the thing a later
   reader most wants to see. Evidence `judgment`.

**Orchestrator's note, passed to the implementer with the finding.** The reviewer's option 1
converts a property-shaped name into an **enumeration-shaped** one, which runs against this
project's standing preference for a property over an enumeration — the backlog records that "the
docblock carries no claim this task falsifies" caught a blocking finding in two consecutive
sessions where an enumeration of known instances would not have, and an enumeration of four
strings in a test name is what goes stale on the next edit to this stylesheet. Option 2 keeps the
name a property and makes it true. The implementer was told to weigh this rather than defer to it,
and to state which option it took and why.

## Round 3 — PASS, no blocking findings. The repo-wide typecheck fix.

**Why there was a third round at all, and whose defect it was.** After T1 passed round 2 and
committed `5073544`, **T4's implementer** found `npm run typecheck` exiting 1 on T1's committed
file: `Composer.styles.test.ts(44,77): error TS18048: 'value' is possibly 'undefined'` — `matchAll`
types every capture group as `string | undefined`, so the destructured `value.trim()` was unsound.
`typecheck:node` passed; `typecheck:web` failed on that one diagnostic.

**No criterion of T1's names `tsc`**, and criterion 9 names a scoped vitest run, which both the
implementer and the reviewer had correctly reproduced as passing. Vitest transpiles without
typechecking, so neither party had an instrument that could see this. The session's repo-wide gate
sits on T5, the DAG tail, and had not run. Escalation **E2** resolved it by re-dispatching T1 at
revision round 2, which is its cap.

### The fix, and the judgment behind it

```ts
const borderWidthDeclarations = (): string[] =>
  [...css.matchAll(BORDER_WIDTH_DECL)].map(
    (m) => `${m[1] as string}: ${(m[2] as string).trim()}`,
  );
```

**It refused `?? ''`, and the reviewer calls that the strongest of its three reasons.**
`BORDER_WIDTH_DECL`'s group 2 is `([^;}]*)`, so an empty capture is already representable;
collapsing `undefined` into `''` would make the impossible case indistinguishable from it, and the
resulting `"border: "` carries no width term, so `BARE_WIDTH_KEYWORD` reads it as a **non-offender**.
A fallback in the offender direction is a silent pass in the one test meant to go red.

The `repo` reasons check out under the reviewer's own count: `m[N] as string` appears at
`beachcomber/Beachcomber.styles.test.ts:62`, `composer/Composer.styles.test.ts:100`,
`helm/Helm.styles.test.ts:43,55`, `lanes/LaneRail.styles.test.ts:42,274,348,416`,
`permissions/PermissionCards.styles.test.ts:82`, `pods/PodBar.styles.test.ts:84` — and **no `?? ''`
anywhere in that population**. T2's `borderValues` is the identical two-group `matchAll` written the
same way, so the two conversion tasks now agree on the expression as well as on the predicate.

**The docblock's soundness claim is accurate:** group 1 wraps the whole property alternation rather
than sitting inside the optional `(?:-top|…)?`, and group 2 is top-level, so no match can omit
either.
