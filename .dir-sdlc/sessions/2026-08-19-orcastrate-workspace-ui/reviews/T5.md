## Judgments the orchestrator asked for

- **The append-stability conflict, and the implementer's resolution: correct.** The contract does state two guarantees that cannot both hold, and criterion 6 does resolve it — a backfill page returning 1-100 after a live 40-45 cannot yield "each seq exactly once, in order" without moving seq 40 from index 0 to index 39. Strict ordering had to win. Preserving object identity across the merge is the strongest form of stability still available once index stability is forfeit, **and it is what actually protects React keys and memo identities — the thing index stability was there to protect.** Documenting the conflict at the head of `merge.ts` rather than silently picking is the right call for a file three peer tasks depend on.
- **Exhaustion keyed on ready-and-not-more, rather than not-idle: reasoning verified, implementation matches.** After a failed page the store sets an error phase and leaves the more-available flag at its initial false, so the looser guard would treat a transient IO error as permanent exhaustion and truncate the transcript with no retry. A test demonstrates the retry succeeding after a failure.
- **Startup auto-activation, explicit `opened` tracking, un-short-circuited `interruptPod`, page size as a constructor option** — all four verified as described. On `opened`: the status union is idle / running / waiting / beached with only beached terminal, so `idle` genuinely cannot distinguish "never opened" from "open and quiet"; tracking it explicitly is not merely defensible but necessary.

## Advisory findings

1. `loadRoutingMode` discards the error on failure (`store.ts:290`): the mode stays null forever with no retry and nowhere for a consumer to see why. The contract's null means "unresolved", so nothing breaks, but a permanent silent null is indistinguishable from a slow startup.
2. `laneList` and `appRoutingMode` are covered for the failed-envelope case but not for the rejecting-preload half of criterion 3. The implementation handles it — both route through the same choke point — so this is a coverage gap, not a behavior gap.
3. The contract says `session` is undefined when the active Pod has not been opened, but the derivation returns a session for an active-unopened Pod. That is the only reading consistent with the contract's own `not-opened` disabled reason, so the resolution is right — flagged so peers know which reading won.
4. `applyEvents` writes a fresh transcript object even when the merge returned the identical array (`store.ts:326`), so a fully redundant push still produces a re-render — defeating the no-op optimization one level up from where it was built.
5. The isolation grep matches the literal `window.orcastrate` only; a bracket access or destructured alias would slip past. Adequate against accident, not against intent.
6. `respondToPermission` reports success when it suppresses an in-flight duplicate, for a call that sent no decision. The contract only requires idempotency, so this is within bounds.
