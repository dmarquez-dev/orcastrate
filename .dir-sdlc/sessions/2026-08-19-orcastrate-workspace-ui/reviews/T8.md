## Blocking finding 1 — criterion 3's rail-order assertion is degenerate

`harness.tsx` gives the Matriarch a `startedAt` **earlier** than both Calves, so the expected rail order is also what a plain `startedAt` sort produces. The Matriarch pin — the defining property of the guaranteed order — is never exercised.

The reviewer mutated `ordering.ts:30` to delete the pin and ran the suite: **`workspace.e2e.test.tsx` stayed green**, while the unit-level `state/ordering.test.ts` correctly went red. This is the one mutation of five spot-checked that did not reproduce T8's claim that all 14 went red.

Ranked options, as the reviewer worded them:

1. **Move the Matriarch's `startedAt` between the two Calves** in `harness.tsx`. The pin then becomes the only thing that can produce the expected order, and the Calf sort stays load-bearing. One line. The fixture is shared by all four suites, so re-run the whole set. *Evidence: repo — `ordering.ts:30-34` sorts on kind then `startedAt`, and `ordering.test.ts:79-81` already covers the pin at unit level with exactly this shape.*
2. **Add a second `laneChanged` push** in the same test whose Matriarch starts last, re-asserting the expected order. Leaves the shared fixture untouched, at the cost of a second assertion block. *Evidence: judgment.*
3. **Accept the gap** and rely on the unit test for the pin, narrowing criterion 3's wording. Cheapest, but criterion 3 is explicitly about the assembled rail — a scope change, not a fix. *Evidence: judgment.*

## Blocking finding 2 — criterion 6's error coverage rests on an inverted justification

The header comment says "four of them have nowhere to surface an error today", but the file asserts the message for exactly **four** channels. If only four lack a surface, roughly eleven have one and seven went unasserted.

At least one such surface is real and unasserted: `TranscriptPane.tsx:140-142` renders `view.error.message`, which is where an `eventsRead` failure lands. By contrast `LaneRail.tsx` renders no error at all, so `laneList` genuinely is silent. **The gap is defensible; the stated reason for it is not.**

Ranked options, as the reviewer worded them:

1. **Audit all 15 channels against their surfaces and assert every one that has a surface**, starting with `eventsRead` via `TranscriptPane`, then correct the header comment to the true count. Turns a wrong comment into an accurate, enforced boundary. *Evidence: repo — `TranscriptPane.tsx:140-142`; error state exists in the store for pods, composer, card, lanes, and backfill.*
2. **Add one executable assertion enumerating the surface-less channels** — a named allowlist the test asserts is exactly the set with no rendered error — so the exclusion is checked rather than narrated and cannot silently grow. *Evidence: judgment.*
3. **Correct the header comment only**, leaving coverage at four and recording the rest for Gate 3. Cheapest and honest, but leaves criterion 6 under-covered where a surface demonstrably exists. *Evidence: judgment.*

## The four defects T8 reported rather than fixed

All four confirmed real at source. **None is a T8 defect** — T8 was right to report rather than patch, and none blocks its own criteria.

- **A — no affordance opens an existing Pod. Real, and the most serious.** The frozen contract declares `openPod`/`reconnectPod`, the store implements them, and grep across the whole renderer excluding tests finds **no caller in any component**. `runtime.opened` is set only by create/open/reconnect, so after a restart every Pod from `pods.list` sits at a permanently disabled composer with no control that opens it. **Classification: a scope gap in the session's definition of done, not a defect in T8 or in any committed task.** No task's acceptance criteria owned "open an existing Pod from the UI", so no implementer failed a criterion — the frozen contract provisioned the action and the decomposition never assigned a view to call it. A decomposition-level miss, which is exactly the class of finding Gate 3 exists to surface. It renders the app unusable across a restart, so it is a product-level defect even though it is nobody's task-level one.
- **B — a failed `app.routingMode()` hangs on the loading state forever.** `store.ts:289-290` returns without retry or error state, and `App.tsx:67` renders the loading view whenever the mode is null. Belongs to the committed task owning those files. It does not contradict criterion 6's case for that channel, which asserts only that the workspace and Pod bar render — and they do.
- **C — the default stub's `pods.open` resets the created Pod.** It returns a fresh stub Pod that the store then merges over the real one, discarding title, cwd, permission mode, and env overrides. A harness-fidelity bug in **T3's committed `test-utils`**, not in the app. T8 diagnosed it and worked around it locally rather than editing another task's file — the right call. Worth fixing at source so the next suite does not rediscover it.
- **D — four channels have no error surface.** Real as a gap, wrong as stated; promoted into Blocking 2.
