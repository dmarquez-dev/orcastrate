## Blocking finding 1 — the dispatch card's per-agent rows are unreachable in the real app

The pane builds its lane index from `view.events` only, and `view` is **one lane's** stream — `App.tsx:38` calls `useTranscript(selectedLaneId)` and `state/store.ts:315` buckets events by `event.laneId`.

But `src/main/lane/lane-router.ts:603` emits `lane_opened` stamped with **the new Calf's own laneId**, and `pod-manager.ts:747-767` deliberately leaves it there — its comment calls redirecting it onto the Matriarch the very bug the drift warning exists to catch. So the Matriarch pane holds the dispatching `tool_use` but never the `lane_opened`. The index comes back empty, the collector returns nothing, and every card falls to a count of 1 with "No agent lanes to show for this dispatch."

The one mode where `lane_opened` *does* carry the Matriarch's laneId is `inline` — which the pane short-circuits to an empty index by design.

Net: in production the per-agent rows never render and the jump callback is never reachable from a card. **The tests pass only because `transcript/test-fixtures.ts:22` defaults every event's `laneId` to the Matriarch, including a Calf's `lane_opened` — an assumption the producer contradicts.**

Ranked remediation options, as the reviewer worded them:

1. **Escalate a contract amendment giving `TranscriptPaneProps` the lane registry it needs (e.g. `lanes: Lane[]`), fed from `PodSessionView.lanes`.** The only route that satisfies the criterion in full, because the row must carry *status*, and status lives on the lane row the state layer already maintains and refreshes on every `laneChanged` push. The pane currently has no legitimate source for it. *Evidence: repo — `renderer-state.ts` already exposes `PodSessionView.lanes` and `useLaneRail()` with a documented ordering guarantee matching the contract's "in rail order".*
2. **Derive the row from the dispatch event itself**: `dispatchedLaneId` for the jump target plus `input.subagent_type` / `input.description` for the label, with status defaulting until a lane is known. No contract change, restores a clickable labelled row today; the weakness is that status is a guess, so it satisfies the click and label halves of criterion 7 but only approximates "carrying its status". *Evidence: repo — `events.ts` documents `Lane.subagentType` and `Lane.description` as coming from the dispatch tool_use input, so the same fields are present on the payload.*
3. **Keep the current derivation and add a fixture-level regression test** that stamps a Calf's `lane_opened` with the Calf's own laneId, documenting count-only as accepted production behaviour. Cheapest and honest about what ships, but concedes that spec 5.2's clickable dispatch card does not exist in `lanes` mode — the mode the product defaults to. *Evidence: judgment.*

## Blocking finding 2 — three test ids are rendered suffixed where the frozen contract specifies them bare

`LaneRow.tsx:67,104,115` emit `lane-row-unread:<id>`, `lane-row-pin:<id>`, `lane-row-steer:<id>`. `TEST_IDS` annotates a suffix on exactly the ids that take one — `podTab`, `podTabPermissionBadge`, `laneRow`, `newPodModeOption`, `transcriptEvent`, `permissionCard` — and leaves these three bare. T8 writes its suite **without seeing the markup**, so a lookup by the contract's id returns zero elements.

The collision rationale does not survive contact with the peers: T7 renders its three action ids **unsuffixed across simultaneously-visible cards** and relies on scoping within the card. T6's own structure is what blocks that technique — `lane-row:<id>` sits on the inner select button while pin and steer are its *siblings* on the list item, so nothing scopeable encloses them. Leaving `dispatchCard`/`dispatchCardAgent` literal while suffixing these three is also internally inconsistent; `dispatchCardAgent` has identical multiplicity and was solved with a `data-lane-id` attribute.

Ranked remediation options, as the reviewer worded them:

1. **Move the `laneRow` id onto the list-item row container and render the three action ids literally, disambiguated by the enclosing row.** Satisfies the contract verbatim, matches T7's established pattern exactly, and gives T8 the scoping it will reach for; the inner select button takes an unlisted internal id, which the contract explicitly permits. *Evidence: repo — T7's card structure, and `TEST_IDS`' own note that adding an unlisted internal id is fine.*
2. **Keep the literal ids on the current sibling buttons and add `data-lane-id` for disambiguation**, mirroring `dispatchCardAgent`. Smaller diff, restores contract-literal binding, makes T6 self-consistent; T8 must then filter on the attribute rather than scope, which is slightly weaker ergonomically. *Evidence: repo — T6's own choice for the same problem on the dispatch card.*
3. **Escalate an amendment documenting these three as suffixed**, as `laneRow` already is. Legitimate if suffixing is the better seam, but it changes a frozen contract for a problem two peers already solved without one. *Evidence: judgment.*

## Advisory findings

1. **The lane collector gathers the full transitive subtree**, so a grandchild lane opened by a Calf's own dispatch would appear under the *parent's* card and inflate its count. Defensible given the singular/array mismatch and documented in `lane-index.ts:34-40`, but over-inclusive against "one row per opened lane" — and moot in practice for the reason in Blocking 1. If option 1 lands there, revisit whether the card should list direct children only.
2. **"dispatched N agents" is unpluralized**, reading "dispatched 1 agents". The determinism argument for T8 is reasonable, but `N === 1` is the *only* count the current code can produce for an unmaterialized dispatch, so the ungrammatical form is the one users will see most. A pluralized string with the count in a stable data attribute gives T8 the same determinism.
3. **The count fallback reports 1 whenever lanes are unknown** — a wrong number stated confidently rather than an unknown. Consider omitting the count when the lane set is empty.
4. **The `1px` hairline and screen-reader clip judgment was right**, and it is repo-wide: `shell/`, `pods/`, `composer/` and `permissions/` all do the same, and `shell/a11y.module.css` documents identical reasoning. In the same class and not disclosed: em letter-spacing in `LaneRail.module.css:25`, `Transcript.module.css:91`, and `pods/PodBar.module.css:147`. Worth **one session-level note that border-width and tracking are outside the token set**, rather than four separate escalations.
5. **The index degradation is graceful and correctly documented**, and count-only matches what the contract mandates for inline mode. The problem is not the degradation; it is that it is the only reachable path.
6. **The load-more button sits between the events and the permission slot** inside the scroll container. Correct for forward-only paging; wrong end if paging ever becomes backward.

None on ownership — T6 touched only `lanes/` and `transcript/`, and edited no frozen contract. Blocking 2 is a deviation from a frozen contract's documented value shape, not an edit to it.
