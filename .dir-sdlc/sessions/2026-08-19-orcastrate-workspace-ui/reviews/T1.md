### FK handling, judged directly

The pragma sequence at `sqlite-event-store.ts:134-158` is correct. `PRAGMA foreign_keys` is read and toggled **outside** `db.transaction()` — it is a silent no-op inside one, so the placement is load-bearing and correctly chosen. `foreign_key_check` runs **inside**, so a genuinely orphaning migration rolls back rather than committing damage. On the throw path better-sqlite3 issues ROLLBACK synchronously before rethrowing, and the `finally` restores the pragma afterwards, outside any transaction, on both paths. `fkWasOn` gating means a caller who had FKs off keeps them off.

The implementer's claim is accurate: unmodified, `DROP TABLE pods` would have cascaded the entire store away, because `lanes.pod_id` and `events.pod_id` are `ON DELETE CASCADE` and the constructor sets `foreign_keys = ON`.

### B1 (blocking) — the byte-identity pin is guaranteed to fail once this branch lands on `main`

`migration-2.test.ts:60-80` (`shippedMigration1`) reads `git show main:src/main/store/schema.ts` and evaluates that blob's `MIGRATION_1` template via `new Function('sqlIn', ...ENUM_NAMES, ...)`. Post-merge, main's `MIGRATION_1` interpolates `MIGRATION_1_PERMISSION_MODES`, which is neither in `ENUM_NAMES` nor exported. The reviewer reproduced this by running the test's own extraction logic against the post-merge content: `ReferenceError: MIGRATION_1_PERMISSION_MODES is not defined`.

It does not degrade to a false pass — it hard-errors — but it turns the suite red on `main` for the next session, and it is equally fragile against a shallow CI clone or any concurrent merge touching `schema.ts`. Violates criterion 4 in substance (the pin does not survive the merge it was written for) and criterion 11 on the very next run.

**Ranked remediation options, as the reviewer worded them:**

1. **Pin the git ref to the immutable commit that shipped migration 1 instead of the moving `main`.** Change the `execFileSync` arg to `96f6e925f75c9b101903116a0522c98971e0f347:src/main/store/schema.ts`. That blob is frozen, so its identifier names can never drift out from under `ENUM_NAMES`, and the assertion keeps exactly the semantic criterion 4 asks for — "identical to the version that shipped." One-line change; the existing renderer keeps working unchanged. *Evidence: repo — that SHA is this task's diff base and is where migration 1 currently lives on `main`.*
2. **Replace the git read with a checked-in golden fixture.** Write migration 1's rendered SQL to e.g. `tests/unit/store/fixtures/migration-1.sql` and assert `migration(1)` equals its contents. Removes the git dependency, the regex extraction, and `new Function` in one move, and works in shallow clones and non-git checkouts. Slightly weaker provenance; the fixture itself must then be treated as frozen. *Evidence: repo — `tests/unit/store/helpers.ts` already exists as this directory's shared fixture surface.*
3. **Keep `git show main` and make the renderer tolerant of per-migration pin arrays.** Scan the blob for every `const \w+_PERMISSION_MODES` / `const \w+ = [...] as const` and pass them all as parameters. Least intrusive, but preserves the moving-ref fragility and each future migration adds another identifier the regex must anticipate. Not recommended. *Evidence: judgment.*

### Advisory findings

1. **The other four enums in `MIGRATION_1` are still live constants.** `schema.ts:141-201` still renders `sqlIn(POD_STATUSES)`, `sqlIn(LANE_STATUSES)`, `sqlIn(LANE_KINDS)`, `sqlIn(EVENT_TYPES)` into shipped DDL, so widening any of those repeats the exact bug this task fixed. The reviewer agrees the hazard is real, with a qualification the implementer did not make: while the pin test works, widening one of those four fails it loudly rather than silently rewriting history — so the pin is a partial mitigation, not a fix, and it only holds once B1 is resolved. Pinning all five per-migration lists in one pass would close the class.
2. **`new Function` is not the problem the implementer thought it was.** The reviewer explicitly disagrees that it warrants action on its own: the input is a blob from the repository's own history, it is confined to a test, and evaluating the old file's own template is precisely what makes the expected value independent of current-build constants — the test's central virtue. Option 2 removes it as a side effect; removing it for its own sake would weaken the pin.
3. **`sqlIn` is used on both sides of the byte-identity comparison**, so a change to its formatting would move expected and actual together undetected. Narrow; a golden fixture would close it.
4. **`PERMISSION_MODES` no longer feeds any DDL** — it survives only as the exhaustiveness anchor for criterion 3. A reader may still reach for it when writing migration 3. Consider renaming to `PERMISSION_MODES_AT_HEAD`.
5. **The contract docblock overstates current reality.** `events.ts:69-71` says each of the four "is selectable in the UI"; there is no renderer mode picker in the tree yet. Accurate as intent, premature as description.
6. **The pragma restore's failure path is correct but untested.** No test injects a throwing migration to confirm `foreign_keys` is re-armed after a rollback. The `finally` makes it correct by construction and criterion 5 only asks for the success path — but it is the one branch of the highest-risk code in this task that nothing exercises.
