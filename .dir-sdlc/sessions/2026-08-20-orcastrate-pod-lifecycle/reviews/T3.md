## The two judgement calls the review was asked to examine

- **Logger seam vs criterion 9 — satisfies it, does not evade it.** Criterion 9 constrains
  `PodRunnerOptions`/`PodRunnerHandlers`, and neither changed. `createPodRunnerWith` lives in
  `src/main/pod/pod-runner.ts`, not in the frozen contract, and its own pre-existing docblock already
  designates it as the sanctioned seam ("not a member of `PodRunner` or a field on
  `PodRunnerOptions` — both are frozen"). The frozen `CreatePodRunner` signature and the production
  `createPodRunner` export are unchanged. The `Pick<Console,'warn'>` + `?? console` idiom is
  confirmed in-repo at `pod-manager.ts:100,185`.
- **`#teardown()` extraction vs `stop()`'s prior behaviour — verified, one narrow divergence.**
  Beached path identical (`#teardown` early-returns, `if (!this.#beached)` skips the status write,
  exactly as the old early return did). Second-`stop()` path identical, because `#setStatus`'s
  equality guard makes the now-reachable `setStatus('idle')` a no-op. `:190`/`:199` throw sites
  identical. The divergence is advisory 1.

## Advisory findings

1. **`stop()` after a failed start is no longer a strict no-op in one reachable corner.** Old `stop()`
   early-returned before `#setStatus`; new `stop()` always reaches `if (!this.#beached)
   this.#setStatus('idle')` (`:446-447`). Invisible whenever status is already `'idle'` — every tested
   path — but if a permission prompt were in flight when `initialized()` rejects,
   `#pendingPermissions > 0` leaves status at `'waiting'` and the subsequent `stop()` would emit an
   `onStatus('idle')` the old code did not. Arguably a fix rather than a regression; criterion 2's
   three stated properties hold either way.
2. **`start()`'s rejection can now be delayed by up to `STOP_GRACE_MS` (2s)**, since `#teardown()`
   awaits `Promise.race([#consumed, delay(2000)])` before the rethrow. Type, code and message are
   unchanged so criterion 3 is unaffected, but a CLI that ignores the abort turns a fast failure into
   a 2s one.
3. **The frozen contract's prose predicts a different mechanism than the one that shipped.** Contract
   section 7 half A states that `stop()`'s trailing `#setStatus('idle')` is suppressed on the
   failed-start path "by the runner's own beached latch (`pod-runner.ts:424`)". In this implementation
   the runner is *not* beached on that path — suppression comes from `#setStatus`'s equality guard
   instead. Same observable outcome (no `'idle'` escapes), different mechanism. **Relayed to T2 in
   flight**, because T2's criteria 10 and 12 reason about this path.
4. `tests/unit/pod/session-id.test.ts`'s `started()` passes `logger` as possibly `undefined` and
   relies on default-parameter behaviour. Explicit, but it means several tests warn to the real
   console if the narrowing ever regresses.
