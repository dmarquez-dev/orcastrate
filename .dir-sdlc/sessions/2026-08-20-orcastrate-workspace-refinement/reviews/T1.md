## The two self-flagged items

**The `App.smoke.test.tsx` recorder — sound.** It is an observation wrapper, not a stub: it
pushes props and then renders `Actual` with identical props via `importOriginal`, so every
pre-existing DOM assertion still runs against the real tree (`transcriptSplit`,
`transcriptPrimary`, `composer` all survive and still assert). It stubs nothing the criterion
meant to be observed, because the criterion's object — three *optional* callbacks — has no
DOM projection at all. `App.panelSlots.test.tsx` makes the identical argument for `panelBar`.
Secondary benefit is real: opening the follower by calling the prop rather than clicking a
control decouples the suite from T2/T3's concurrent rewrite of that markup.

**`patchRuntime` throwing — right severity.** Criterion 6 asks for the policy *asserted*, and
a throw is the strongest available assertion; repairing silently is the failure mode this
session was convened around. The reviewer confirmed the throw is unreachable from any action:
`repairSelection` is the only writer of `primaryLaneId` and writes exactly what
`assertPanePolicy` checks, and the cap cannot be exceeded by `showLane` (pushes only below
`MAX_FOLLOWER_PANES`) or `hideLane` (only removes). A genuine logic-error tripwire, not a
runtime input validator. One note in advisory 3.

## Blocking

### B1 — Criterion 13 is unmet, and unmeetable by T1 without a contract violation

`vitest run` is 4 red and `typecheck:web` is 15 red at the end of T1. Every one of those 19
lives in `lanes/**`, `transcript/**` or `__tests__/**` — T2's, T3's and T5's ownership sets.
Criterion 13 as written asks T1 to leave a suite green whose red is caused by criteria 1, 2
and 9 doing exactly what they were written to do, and whose only fix is editing three other
tasks' files.

**Ranked remediation options, as the reviewer worded them:**

1. **Re-scope criterion 13 to T1's own files, and re-assert the whole-suite version as a
   DAG-exit gate after T2/T3/T5 land.** *Rationale:* this is the criterion the diff actually
   satisfies (8/8 suites, 241/241, zero type errors in owned files), and it preserves the
   check that matters without asking T1 to cross an ownership line. The full-suite assertion
   does not disappear — it moves to the only point in the DAG where it can be true.
   *Evidence:* `repo` — `renderer-panes.ts` names T2/T3/T5 as consumers of exactly these
   symbols, and the contract's own optional-prop concession ("a required prop would leave
   whichever landed first red until the other landed, which makes a task unreviewable")
   states this failure mode explicitly as an accepted cost of concurrency.
2. **Keep criterion 13 as written but record the 19 failures as an accepted, itemized
   carry-forward against T2/T3/T5, each mapped to the criterion that caused it.**
   *Rationale:* same practical outcome, more auditable — the list becomes a checklist the
   consumer tasks are measured against rather than a footnote. Costs more bookkeeping and
   leaves T1 formally short of a criterion. *Evidence:* `repo` — this session already keeps
   per-task reviews under `reviews/`, so there is a place for the list to live.
3. **Send T1 back to fix the 19 call sites.** *Rationale:* the only option that makes
   criterion 13 literally true in this task. **The reviewer does not recommend it** — it
   requires T1 to edit `lanes/**`, `transcript/**` and `__tests__/**` while T2, T3 and T5 are
   running against those same files, which is the corrupting-a-concurrent-peer case, and it
   would pre-empt the acceptance criteria those tasks are being judged on.
   *Evidence:* `judgment`.

## Advisory

1. **The criterion-4 "seen to fail first" claim cannot be checked, and unlike criterion 9's it
   is weak on its own terms.** The probe file is deleted, so the reviewer could not reproduce
   it — *state that plainly at the gate rather than repeating the claim.* The distinction
   worth recording: criterion 9's shipped assertion (`podOpen` empty) is itself a valid
   discriminator against the old code, because `createPod`'s signature never changed;
   criterion 4's is not, because `showLane` did not exist before, so against the pre-change
   store it dies on `showLane is not a function` rather than on a swap. The shipped test still
   discriminates against a **reintroduced** swap, which is the regression that matters going
   forward — it just does not evidence the historical claim.
2. `App.panelSlots.test.tsx:12` still reads "It is the one file in the shell that mocks a
   sibling component". Now false, and the file is inside `shell/**` (T1's set), so it was
   correctable. One sentence; no criterion touches it.
3. `assertPanePolicy`'s throw escapes through `patchRuntime` into push subscription callbacks,
   which nothing wraps — `safeInvoke` only guards the invoke boundary, and its own docblock
   states the principle of not letting a throw escape "inside a click handler". Deliberate and
   provably unreachable today, but if a later task adds a second writer of `runtime.lanes`,
   the failure mode is a blanked renderer rather than a repaired pane. Worth a line in the
   state layer's notes for whoever holds the cap change.
4. `repairSelection`'s `const focused = …` (`store.ts:1032`) and `workspace-provider.tsx`'s
   `canPin:` expression are wrapped inconsistently with surrounding code. Cosmetic; the repo
   has no Prettier dependency or config, so nothing enforces either way.
