## The three self-flagged items — explicit verdicts

**`'not-requested'` at the handler: faithful, not a gap.** The frozen `PodSessionRemover` is
`(pod: Pod) => …` and carries no `deleteSession`, so no reading of criterion 4 lets the port
decide it without breaking the frozen signature. The assertion is not vacuous:
`pod-deletion.test.ts:109-143` injects the **real** `createPodSessionRemover` over a temp
tree and writes the actual file the Pod's `cwd`/`ccSessionId` point at, so a handler that
wrongly called the port would have binned a file that exists and `expect(binned).toEqual([])`
would go red. Testing "nothing happened" against the real code path with the target genuinely
present is the stronger form, not the weaker one.

**The `.catch` in the reject rig: hides nothing, but narrows that rig.** `listPods` is
synchronous on `PodManagerApi` (`pod-manager.ts:123`), so the rig's `boom` returning a
rejected promise was never a faithful stand-in; `pod:delete` calling `.find` on it throws a
`TypeError` synchronously, which `register` still converts into the `ok: false` envelope the
rig asserts. The assertion holds, and for a real reason. The consequence is that in *both*
modes `pod:delete` now fails at `listPods` and never reaches `manager.deletePod` — which
makes the rig's new `deletePodSession: boom` line dead. That would be a genuine hole if
nothing covered it, but `:276-351` asserts exactly the uncovered case. Advisory, below.

**Per-character encoding: correct, and the prose is what is wrong.**
`beachcomber/paths.ts`'s docblock says "non-alphanumeric run", but its own
`decodeDirectoryName` regex `/^([A-Za-z])--(.*)$/` requires **two** dashes for `C:\`, which
only per-character encoding produces. Confirmed against live data, including the
`dir-ect--claude-worktrees` case where `\` + `.` produce two adjacent dashes from a
two-character run.

## Advisory findings

Recorded here, not fixed. Carried to Gate 3 for the user to defer or drop.

1. **A knowing deviation from the frozen contract's wording.** `ipc.ts`'s
   `PodSessionRemover` docblock reworded the contract's "called AFTER the row is read and
   **BEFORE it is deleted**" into "AFTER the row has been read **and deleted**", and the
   implementation follows the new wording. The reviewer judges this the right call — the
   frozen contract is self-contradictory here, since §3 orders path-resolution before
   `deletePod` while the port both resolves and trashes, and `handlers.ts` may compose no
   path — so the two readings cannot both hold, and the implementer preserved the
   load-bearing one (trash last, row captured first). Worth recording as a knowing deviation
   rather than a silent rewrite, because the frozen file still says the other thing.
2. **A factually wrong label on an unreachable branch.** `handlers.ts` returns
   `session: 'not-requested'` when `pod === undefined` even if `deleteSession` was true.
   Unreachable — `manager.deletePod` answers `NOT_FOUND` first, pinned at
   `pod-deletion.test.ts:92-102` — but the label would be wrong if the branch ever became
   reachable.
3. **A comment describing a payload its entry does not use.** In `envelope.test.ts`, the
   added comment about `deleteSession` never being defaulted sits below
   `[INVOKE_CHANNELS.podDelete]: [null]` and immediately above the `podOpen` entry. The case
   it describes is exercised in `pod-deletion.test.ts`, not there.
4. **Dead coverage that reads as live.** `deletePodSession: boom` in `rigThatThrows` is never
   reached in either mode, because `pod:delete` now fails at `listPods` first. Harmless, but
   it reads as coverage it does not provide.
