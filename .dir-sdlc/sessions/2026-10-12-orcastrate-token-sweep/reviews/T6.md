## Criterion 6 — the reviewer's explicit ruling

> **The equivalence is genuinely demonstrated, and the criterion is defective as written.**

Demonstrated on all three points: the literal reference **exists and is measured, not
asserted** — `probePixelGrid()` creates real divs in the live window
(`position:fixed;left:-9999px`), declares `border-width:1px`, reads
`getComputedStyle(d).borderTopWidth`, removes them, and `ONE = grid.oneCssPx` is set from
that reading, with **every** downstream border check comparing against `ONE` and never the
string `"1px"` (the reviewer checked every `check(` call touching a width). It is the **same
window, same run** — TS-1, before any stateful step. And the ladder is real:
`1px→0.8, 2px→1.6, 3px→2.4, 4px→4, 5px→4.8`, each from its own synthetic element, plus
`var(--oc-border-hairline)→0.8px` with an explicit passing equality check against the
literal — fitting `floor(declared×1.25)/1.25` on all five rungs, arithmetic the reviewer
checked by hand.

So **in this window no 1px border computes to `1px`, a literal one included.** A literal
reading of criterion 6 is satisfiable only on a different display or by a defect, and in the
first pass it produced 8 false failures — one of them against a synthetic literal `1px`.

> **On the authoring defect: yes, record it.** Criterion 6 hardcodes a pixel value in the
> same task where criterion 4 explicitly forbids hardcoding one for the analogous
> measurement. The two cannot both be honoured on their letter, and the method criterion 4
> mandates is the one that makes criterion 6's intent measurable.

The reviewer declined to rule the criterion met on its own reading of intent — the verdict
stays `not met` on the letter and the question went to the orchestrator as **E3**. It costs
**no revision round**: nothing in the implementation would change.

**This is the third defective criterion this project has frozen in two sessions**, after
C3's arithmetically-impossible count and its "five directories" naming four. The discipline
that would have caught it is the one C3's own process note names — simulate a criterion's
numbers before freezing, including the ones that look unarguable. `1px` looked unarguable.

## Advisory findings

**A1. A reachable converted declaration is reported as a limit — the same class as harness
fault 2.** `transcript/Transcript.module.css:45-51` is a **grouped** selector:
`.filterToggle, .unpin { … border: var(--oc-border-hairline) … }`. The driver enumerates it
only as `.unpin` and reports "not reached — needs a SPLIT pane", but `.filterToggle` renders
unconditionally in the pane header (`TranscriptPane.tsx:175-181`), and TS-5 measured `.pane`
and `.paneHeader` as rendered in that very state — so the declaration **was** on screen and
measurable. This understates coverage, which is the conservative direction and violates no
criterion (criterion 8 forbids claiming an unseen site, not missing a seen one). Scope is
bounded and positive-controlled: the reviewer grepped the 6-line context above every hairline
declaration in all 7 files for comma-grouped selectors and `Transcript.module.css:45` is the
**only** one. Next session: declaration-keyed enumeration, or enumerate every selector in a
group.

**A2. The ambiguity remedy is loud, not fatal — and the prose overstates it.**
`resolveHashes()` + TS-0 turn an ambiguous or absent signature into a failing check, a
`harnessFaults` entry and `process.exit(1)`, which does kill the silent-drop mode. But the
plan loop still skips the file (`if (!h) continue`), so the file **is** still dropped — just
no longer quietly. FINDINGS says "failing loudly on ambiguity instead of dropping the file",
claiming more than the code does. The disambiguation itself is sound and verified: all 7
signatures resolved to exactly 1 candidate; `.empty` does exist in both
`shell/EmptyWorkspace.module.css` and `helm/Helm.module.css`, and `Helm.module.css` carries
**none** of `heading`/`body`/`action` (0 hits, exit 1, positive-controlled against 4 hits in
EmptyWorkspace), so the 4-class signature genuinely disambiguates the file that broke the
first pass. `.dialog`/`.error`/`.button` exist in both pod dialogs and `.pane` in both
`WorkspaceLayout` and `Transcript`; the sweep's match token `_<cls>_<hash>_` is hash-gated
and `_`-terminated, so neither cross-file nor prefix collision is possible.

**A3. The mechanism behind the `0.8px` is inferred while the document states it as fact.**
FINDINGS says "this display is fractionally scaled", but the run's own reading is
`devicePixelRatio = 1.0000000149011612`, which is in tension with that. The quantization is
measured and the `×1.25` fit is exact on all five rungs; the **cause** is not measured. One
sentence downgrading it to an inference would cost nothing, and criterion 6 does not depend
on it.

**A4. An intended check never ran, and its pointer is stale.** TS-0's note defers the
live-element/bundle hash agreement to "TS-4", but the rail renders at TS-5 and no such check
exists in either step, so `check('the live .railHeading element carries the SAME file hash…')`
never executed. The claim is still substantiated — the TS-5 sweep hit for `.railHeading` is
gated on `_railHeading_1h7yc_`, and TS-3 printed `_podBarRegion_l2fht_35` verbatim, a token
present only in the worktree bundle — but by a different artifact than the document points at.

**A5. A few counts carry no named command.** The A/B screenshot byte figures ("differ by 7
bytes (28,602 vs 28,609)") are accurate — the reviewer confirmed them with `ls -la` — but
neither the provenance table nor the sentence names what produced them. C3's `20/23` and
`3 of 10` are cited correctly from `FINDINGS-C3.md:76,94`.
