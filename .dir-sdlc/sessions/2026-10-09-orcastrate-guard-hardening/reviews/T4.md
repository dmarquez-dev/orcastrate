## Advisory findings

**A1 — The self-reported `git checkout` is advisory, not blocking.** Process
finding, not a diff line. The reviewer verified all three mitigating facts rather
than accepting them: `ea06303` is both HEAD and the last peer commit, so no peer
was in flight and **the `index.lock` race the rule exists to prevent was
structurally impossible on the DAG tail**; `git checkout -- <paths>` is a
working-tree-only write that cannot alter index or commit state; and the two files
are byte-identical to HEAD now. No acceptance criterion is unmet — C4 *required*
that revert — no frozen contract was touched, and no peer was corrupted, so none
of the three blocking classes fires. Touching the two files was sanctioned by C4
itself; only the revert mechanism was wrong.
**The correct non-git revert was available:** the injection was a one-byte append,
so `truncate -s -1 <file>` is its exact inverse, and the reviewer confirmed
`/usr/bin/truncate` (GNU coreutils 8.32) is present in this environment. The
generally correct pattern, covering in-place as well as append-only injections, is
to copy each target into the assigned scratch directory before injecting and copy
it back afterward.

**A2 — The implementer's independent `grep -lP` corroboration was vacuous in this
environment.** `grep -lP '[\x00-\x08…]'` fails here with
`grep: -P supports only unibyte and UTF-8 locales` and **exit 2** — it matches
nothing regardless of content, which the reviewer confirmed with a positive-control
file containing a literal `0x08`. So the "every file under both roots is clean,
`.ndjson` included" evidence cited for C2 and C5 — **and the sentence recording it
in the shipped docblock** — rested on a command that cannot report a hit. Neither
verdict changes: the reviewer reproduced the same conclusion with a Node sweep
carrying a positive control, and **the conclusion holds**. Recorded so the
docblock's claim is not later trusted as a measurement that was actually taken.

**A3 — The `.ndjson` fidelity argument justifies not failing the build, but leaves
those ten files with no integrity signal at all.** The exclusion clears C2's bar:
"is a verbatim recording of an external process's stdout" is an intrinsic property
of the file's role, and it matches this file's own established logic for not
flagging `▾`/`…`/`—` — a guard whose correct resolution is sometimes "leave it" is
a guard that gets switched off. The tension is real, though: the original incident
was a scripted edit and these fixtures are machine-written, so they share the
exposure. The residual gap is that an unintended mutation of a recording is now
invisible. **A checksum or byte-length assertion over the fixture set** is the
right instrument — it catches any unintended change, control byte or not, without
asking a rule to distinguish defect from data. A separate decision, outside this
task.

**A4 — `probe`'s floor of 5 against 8 files is loose, but catches more than the
ratio suggests.** It satisfies C3 as written, whose stated purpose is an *absent*
root: missing or renamed → ENOENT → `[]` → `0 > 5` fails. For partial deletion the
margin is 3 files, and the realistic case trips it — losing `probe/agents/` takes
3 `.md` files, leaving 5, and `5 > 5` is false. Losing only
`probe/evidence/foreground-analysis.json` (7 files) would pass silently. The
implementer's rationale — a floor tracking the exact count turns every legitimate
addition into a failure — is sound and was flagged as an assumption. If the two
concerns ever want separating, `> 0` per root plus a distinct inventory test is the
cleaner split.
