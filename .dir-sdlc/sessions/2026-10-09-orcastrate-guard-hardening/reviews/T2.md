## Advisory findings

1. **Which of the two new assertions is load-bearing.** The
   `expect(keptRows[0]?.textContent ?? '').toContain(KEPT_POD_PROMPT)` check is a
   round-trip of a string the test chose, so it proves the store→IPC→render path
   carried *that value* rather than that the renderer produced content of its own.
   It clears criterion 2 as written — the test never writes the string into the
   DOM — but the falsifiability that actually matters for "the renderer stopped
   rendering the kept pane" rests on the `toBe(1)` row-count assertion above it,
   not on the `toContain`. Worth knowing which is which if either is loosened.
   `src/renderer/src/__tests__/pod-stop.e2e.test.tsx:862`
2. **`toBe(1)` will fail on any future setup change** that gives the kept Pod a
   second row, including one unrelated to this guard. Chosen deliberately over
   `toBeGreaterThan(0)` and documented. Flagged so a later failure here is read as
   a setup change rather than a regression.
   `src/renderer/src/__tests__/pod-stop.e2e.test.tsx:856`
3. **The implementer's out-of-scope finding is correct and worth preserving.**
   Moving the `send` to after `mountWorkspace` would both perturb
   `world.calls.eventsRead` and destroy the new control's falsifiability, since
   the row would then arrive by push rather than by the backfill read the
   injection suppresses. Captured in the code comment at
   `src/renderer/src/__tests__/pod-stop.e2e.test.tsx:766-770`.
