## Findings

**Blocking: none.**

**Advisory 1 — the `decodeDirectoryName` docblock is now orphaned.**
`src/main/beachcomber/paths.ts:52-57` — the "Best-effort inverse… Callers must
label the result" comment still sits where it was, but `PodBlockingSubject` and
`podBlockerFor` were inserted between it and `export function
decodeDirectoryName` at `:122`. It now reads as documentation for the interface
that follows it. Moving those ~55 lines above it, or the comment down to `:121`,
fixes it. No criterion covers comment placement. No options — advisory.

**Advisory 2 — which Pod is named as `blockedBy` can change in a multi-Pod R2 case.**
`paths.ts:117-120` — both comparisons run per-pod inside one loop, so for a
decoded `projects` entry where pod A matches by encoding and a later pod B
matches by normalized path, the old code returned B and the new returns A.
**Blocked-ness is unchanged** — that is R3's actual property, and it holds —
only the identity reported in `blockedBy`. Criterion 9 exempts cases covered by
R2, so this is not a violation. Noted because the union argument in the docblock
reasons about refusal, not about which refuser is reported. No options — advisory.

**Advisory 3 — the `pod-session` barrel pulls `createPodSessionRemover` into
beachcomber's module graph.** `paths.ts:30` — R6 mandates the barrel, so this is
contract-directed, and the remover is inert without an injected `TrashItem`, so
`no-destructive-api.test.ts` is not weakened. Worth knowing only if that test is
ever widened to transitive imports. No options — advisory.
